ReliefOffice keeps its original document encoders and parsers. The platform layer maps the file operations they need to Windows handles and UTF-16 paths, with UTF-8 at the application boundary. It does not use the active ANSI code page for filenames.

The declarations and structures come from the public Microsoft Windows SDK and WDK contracts for `NtCreateFile` / `OBJECT_ATTRIBUTES.RootDirectory`, `GetFileInformationByHandle`, `GetFileInformationByHandleEx` / `FILE_BASIC_INFO`, `SetFileInformationByHandle` / `FILE_RENAME_INFO` / `FILE_DISPOSITION_INFO`, `GetSecurityInfo`, `SetSecurityInfo`, `LockFileEx`, and `FlushFileBuffers`. The project SDK headers supply these declarations. No structure or offset is reconstructed from a binary.

Public references: [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile), [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex), [ReOpenFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-reopenfile), [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo), and [_beginthreadex](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/beginthread-beginthreadex?view=msvc-170). These references were fetched successfully during implementation.

Relative opens use the already opened parent directory. Non-following opens reject all reparse points. File stamps use the volume serial, full 64-bit file index, size, last-write time and change time; the timestamp resolution is 100 ns. Protected recovery files and directories use a DACL granting the current process user and SYSTEM access, with inheritance only within a protected directory. Ownership checks derive the same stable 64-bit identifier from the actual owner SID and the current user SID. A filesystem that cannot report or apply the required security fails the recovery operation.

Ordinary file metadata remains available when the filesystem rejects security queries with `ERROR_INVALID_FUNCTION` or `ERROR_NOT_SUPPORTED`. Such objects report an unknown owner (`UINT64_MAX`) and public permission bits, respecting the file's read-only attribute. They never report private recovery permissions. Other security-query failures retain their error. Capability flags alone do not replace an actual security query.

`set_document_mode` applies ordinary document permissions through strict `fchmod`. It accepts an unsupported operation only after a second metadata query proves that the object is a regular file with an unknown owner and public read/write or read-only permissions. This permits user-requested document saves on FAT without claiming confidentiality. Recovery paths retain strict `fchmod` and private owner/mode validation. `reliefoffice_io <fixtures> <work> --public-volume` runs the six non-Math document save/roundtrip suites on such storage and additionally requires strict private-file and private-directory rejection. Word and Excel recovery locks must fail with the actual unsupported-security error; PPT must refuse a file outside its fixed private recovery directory. This PPT case does not exercise a DACL operation on FAT.

An actual AMD64 ReliefWin run established the unsupported-security case: the FAT fixture had ordinary attributes `0x20`, and both `GetFileInformationByHandle` and `GetFileInformationByHandleEx(FileBasicInfo)` succeeded; `GetSecurityInfo` returned `ERROR_INVALID_FUNCTION` (`1`). The former unconditional security query made ordinary `fstat` fail with UCRT `ENOSYS` (`40`). This was not `ELOOP`, whose UCRT value is `114`. On the same run, NTFS returned actual owner/DACL information successfully despite its volume flags omitting `FS_PERSISTENT_ACLS`, so those flags alone are not used to infer whether file security works.

The same run exposed a separate `ReOpenFile` defect: reopening a real NTFS directory with `FILE_FLAG_BACKUP_SEMANTICS`, for either attributes or `WRITE_DAC`, failed with `ERROR_ACCESS_DENIED` (`5`), preventing strict directory `fchmod`. The public Microsoft contract explicitly permits directory handles with that flag. The implementation now sets `FILE_NON_DIRECTORY_FILE` only when the flag is absent. The actual standalone API regression against the old guest DLL executed 72 checks with exactly two failures and no skips: the attributes-only and `WRITE_DAC` directory reopen cases. The regression additionally exercises ordinary file identity/data, synchronous and overlapped access, backup/reparse flags, invalid attribute flags, and directory rejection without backup semantics. The subsequent actual guest run with the corrected DLL passed 90 checks with zero failures and zero skips. This is a ReliefWin baseline, not a Windows 11 comparison.

The corrected directory reopen then exposed an adapter access-mask error. On an actual NTFS directory, `WRITE_DAC | FILE_READ_ATTRIBUTES` (`0x40080`) reopened successfully but `SetSecurityInfo` returned `ERROR_ACCESS_DENIED` (`5`); adding `READ_CONTROL` (`0x60080`) succeeded; adding `WRITE_OWNER` instead (`0xc0080`) still failed. The existing `advapi32/security.c` propagation regression also distinguishes a write-DACL-only handle from one retaining read-control access. `fchmod` now retains the `READ_CONTROL` already required by the adapter's metadata handles when reopening them for a DACL update. It does not request `WRITE_OWNER` or change ntmarta behavior. This guest evidence does not replace a Windows 11 baseline.

After enlarging the fixed test payload, the standard MBR/FAT16 partition mounted as `F:`; the guest's actual `mountvol` output confirmed that assignment. Scripts that still used `D:` could not find the payload. The partition and FAT directory were readable without changing the filesystem driver. The earlier full 8 MiB payload had truncated logs, which are not counted as complete test runs.

Same-directory commits rename the open source handle, replacing an existing destination only when requested. No-replace reservations use the same handle operation without replacement, so recovery does not require hard-link support. File writes use write-through handles and call `FlushFileBuffers` before replacement. Windows has no supported equivalent of POSIX directory `fsync`; the directory-sync call validates the handle and succeeds without claiming a directory flush. Power-loss durability of the final namespace update remains unverified.

Todo and its Diagram/Math++ callers copy each request into a joinable worker. The UI consumes the result only after the worker has completed and joined. Destruction joins an outstanding operation, so it cannot terminate an active save. PNG encoding copies pixels before entering a worker and keeps FLTK drawing on the UI thread. Math++ numeric calculations run in a separate copy of the executable using inherited private pipes; this preserves cancellation and the existing 20-second timeout. That worker validates the transferred expression before evaluation.

All save paths acquire a nonblocking transaction lock before checking the expected stamp and retain it through replacement and cleanup. A `.reliefoffice-locks` directory in the destination directory holds one record with the exact target filename. Transaction directories and records inherit the destination permissions; they impose no additional owner restriction on shared document directories. Records open for read access, which is sufficient for the documented exclusive `LockFileEx` operation. This uses the destination filesystem's own name and case rules and permits saves to different files. Existing targets also acquire an identity lock. Windows uses a `Global` named mutex keyed by the actual volume serial and 64-bit file ID, with only `SYNCHRONIZE | MUTEX_MODIFY_STATE` granted and requested for participating users. A process-local list protected by an SRW lock rejects recursive acquisition through another alias on the same thread. A nonblocking wait accepts normal or abandoned ownership. `FindFirstFileW` resolves the filesystem-selected canonical long name; checked `FILE_ID_BOTH_DIR_INFO` batches from the already opened parent directory provide the file ID. Acquiring the identity lock never opens the target file. POSIX retains its advisory `flock`. Hard-link and short-name aliases share the identity. Production lock scopes are destroyed on their owning thread after saving or failure; workers are joined rather than terminated. Lock records remain after release; unlinking them could split ownership between old and newly created file objects. Writers outside this protocol can still change a target between a stamp check and a namespace operation.

The Microsoft [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) contract states that a classic rename cannot replace a target with open handles. The former Windows identity byte lock retained such a target handle and prevented overwriting. The complete native diagnostic reported 102 Excel saves failing specifically at replacement with `Permission denied`; the separate replacement-under-`SaveLock` regression failed with `EACCES` as well. The new mutex avoids retaining that handle. Using directory entries for identity also avoids a losing contender leaving a transient target handle open while another saver replaces it. The source trace establishes removal of those opens; tests do not prove all possible external-reader interleavings. Ordinary outside readers remain subject to the filesystem's documented sharing and rename rules.

Public contracts for the added operations are [FILE_ID_BOTH_DIR_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_both_dir_info), [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [FindFirstFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfilew), [CreateMutexExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexexw), [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject), and [kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces). No native API declaration, directory structure or offset is reconstructed.
